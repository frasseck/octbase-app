### 2. Self-service password reset (`internal/auth`)

- Migration `027_password_reset`: `password_reset_tokens` (`token_hash` PK — store a hash, never the raw token, same posture as MFA recovery codes; `user_id` FK, `expires_at`, `used_at` nullable, `created_at`). Single-use, 60-minute TTL.
- `POST /api/v1/auth/forgot-password` — public, body `{email}`. **Always returns 202 with the same body** whether or not the account exists or is disabled (no user enumeration). Internally: rate-limit by IP via `shared.ipRateLimiter` *and* cap outstanding tokens per account (e.g. invalidate prior unused tokens on each request); on a real active account, mint token, store hash, email the accept link (`<frontend origin>/#/reset-password/<token>`) through `internal/mailer` following the invitation-email pattern. With blank SMTP the token URL lands in stdout — that's the existing dev-mode contract, keep it.
- `POST /api/v1/auth/reset-password` — public, body `{token, newPassword}`. Validates hash+TTL+unused, applies `shared.ValidatePassword`, sets the new bcrypt hash, marks token used, and **revokes all refresh tokens for the user** (a reset after compromise must end existing sessions). Stable error codes: `RESET_TOKEN_INVALID` (covers expired/used/unknown — don't distinguish), plus existing password-policy codes.
- Both routes join `login`/`refresh`/invitation-accept in the JWT-middleware public list. Write an `audit_logs` entry on successful reset (state change on an account — same standard as the MFA enable/disable events). OpenAPI entries + integration tests (real chi + Postgres per `internal/testutil`, no mocks): happy path, expired token, reused token, unknown email returns 202, rate limit trips.
- Frontend: "Forgot password?" link on the login form → email-entry view → generic confirmation; new `#/reset-password/<token>` route (public, like `#/invitations/<token>/accept`) with new-password form. Mirror both in `octbase-mobile`. i18n strings in `en` + `de` for every new surface.

### 4. Sprint reports — burndown + velocity

- `GET /api/v1/sprints/{sprintId}/burndown` — for `ACTIVE`/`COMPLETED` sprints (422 `SPRINT_NOT_STARTED` for `PLANNED`): returns the sprint window (`startDate`→`endDate`), total committed task count, and one point per calendar day: `{date, remaining, ideal}` where `remaining` = committed tasks not yet `DONE`/`ARCHIVED` at end of that day, reconstructed from `activity_entries` status transitions within the window, and `ideal` is the straight line from committed to 0. Verify first what `internal/activity` records on status change; if from/to status is missing from `payload_json`, add it (forward-only) and state in the OpenAPI description that pre-release history renders approximately. Server-computed on read — no new table, no snapshot job; a sprint is small (bounded by board scope) and the query is indexed by `(project_id, created_at)`.
- `GET /api/v1/projects/{projectId}/reports/velocity` — last N (default 6, cap 20) `COMPLETED` sprints, straight from the snapshotted `committedCount`/`completedCount`: `[{sprintId, name, endDate, committed, completed}]`. No computation to invent — this is a projection of migration 015's data.
